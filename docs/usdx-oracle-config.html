3. Why direct instructions are the right channel for credentials

The FCC spec describes direct instructions as messages "signed by one or a group of signers… which already has attached all required signatures and can be sent by anyone to a TEE proxy", used "for specific configurations or setups". That is precisely this case. Compared with routing credentials through the on-chain sender:

Direct instruction (chosen)On-chain instruction
Credential on-chainNeverAs ciphertext, permanently
CostNoneRegistry fee + gas per rotation
AuthorisationAdmin signer threshold, checked by the extensionContract access control
Rotation latencyImmediate — one HTTP POSTA transaction, per machine
Contract surfaceNone — the sender stays minimalAnother owner-only setter to get wrong

It also keeps UsdxInstructionSender smaller: it needs requestPriceUpdate() and setEndpoints(), and no secret-handling path at all.

4. The SET_SECRET envelope

"The submission can be done by anyone." That is the spec's wording for /direct-instruction. Authorisation comes entirely from the signatures attached, so the message must be self-authenticating and the extension must verify it. The FCC guarantee that a data-provider threshold signed the message applies to instructions only — a direct action carries no such guarantee, and the spec puts the enforcement burden on the extension explicitly. 
struct SecretEnvelope {
    bytes32 domain;     // keccak256("USDX_ORACLE_SET_SECRET_V1")
    uint256 chainId;    // environment binding — Coston2 envelope invalid on mainnet
    address teeId;      // this machine only
    bytes32 keyId;      // "HEX_API", "RPC_QUICKNODE_FLARE", ...
    uint64  version;    // monotonic per (teeId, keyId)
    uint64  issuedAt;   // freshness bound — see §7
    bytes   secret;     // ECIES ciphertext to teeId's public key
}

digest  = keccak256(abi.encode(envelope))
message = abi.encode(envelope, signatures[])     // M-of-N over digest

Verification order — all of it, before touching the secret

The result must disclose nothing. ActionResult.Data nil, and the log a fixed string. Finding 1 established that ActionResult.Log is a public surface that has already leaked a query-string credential once. A SET_SECRET failure must not echo the keyId's value, the ciphertext, its length, or a decrypt error containing either.

The admin signer set

Baked into the image, so the code hash answers "who may set credentials" without an on-chain lookup — a nice property: the authorisation policy is as publicly verifiable as the price rule. Changing the admin set requires a new code version, which is correct for something this privileged.

Open: M-of-N values. Suggest 2-of-3 to start — one signer being unavailable must not block an emergency rotation, and one signer being compromised must not permit one.

5. Endpoints on-chain, and why there is deliberately no host allowlist

Many RPC providers embed the credential in the URL — https://<sub>.quiknode.pro/<key>/, rpc.ankr.com/flare/<key>, ?dkey=. Since endpoints are published on-chain, the URL and the credential must be separated:

on-chain:   { "id": "quicknode-flare", "chain": 14,
              "template": "https://example.quiknode.pro/{KEY}/" }
credential: keyId "RPC_QUICKNODE_FLARE"  → delivered by direct instruction

in enclave: url = template.replace("{KEY}", credentials[id])

The public record then says "we query QuickNode's Flare endpoint" — the fact worth verifying — while the credential never appears anywhere public. Unkeyed endpoints carry no placeholder and need no credential.

There is deliberately no host allowlist. An earlier build baked one; it was removed so that adding a provider (Alchemy, say) or moving from 2-of-3 to 2-of-4 needs no rebuild and no re-attestation. The consequence, accepted on purpose: whoever holds the setEndpoints owner key can name any https host — including one they control — and any threshold, and the attested code will faithfully compute and sign the resulting price. The feed is therefore only as trustworthy as the owner key as well as the TEE (Findings §15); the planned diversity rule (k distinct operators per chain) was not implemented either. What still holds regardless of host choice: https only; redirects are never followed, so an honest host cannot bounce a credential to a third party; {secret} may not appear in a URL's scheme or host; thresholds are bounded by the provider count. A hostile host named directly in a template is the owner's choice, covered by the trust statement above.

This is also finding 2's territory: a redirect can hand the credential to a third party. The implementation never follows redirects on these requests, so the only way a credential reaches a hostile host is if the owner named that host in the template.

6. Should the credential still be encrypted?

Recommendation: yes — keep ECIES, on the direct-instruction channel. Direct instructions remove the on-chain exposure, the gas and the latency, which is the substantive win. Dropping the encryption on top of that is a separate trade with a poor ratio.

Three concrete reasons, beyond principle:

  1. The proxy persists the queue. The FCC spec: "The queue data is persistently stored in the database (REDIS)." A plaintext credential therefore sits at rest on an ordinary VM — reachable through a Redis compromise, a snapshot, or a backup, none of which are enclave-protected.
  2. It forfeits an attestation claim. "The operator could not have seen the API key" is one of the three things the TEE buys us. The spec is explicit that "the owner of the TEE machine also owns the corresponding TEE proxy" — so plaintext-through-proxy means plaintext-to-operator, by construction.
  3. It is what makes automated re-provisioning safe — see §7. An untrusted keeper can hold and replay a ciphertext envelope without ever learning the credential. Holding a plaintext envelope would make the keeper a credential store, which is exactly the authority we designed it not to have.

The cost of keeping it is close to zero: the teesecret CLI in extension-apikey already does the ECIES encryption against the machine key published in the proxy's attested /info, and off-chain delivery means no gas either way.

If you still want plaintext, exactly one field changes — secret carries the raw bytes and step 8 skips /decrypt. Everything else in §4 stands, and the ordering, freshness and signer checks matter more in that case, not less. Note it also collapses §7's automation option.

7. Restart, replay and re-provisioning

Credentials live in memory and do not survive a restart. The extension has no persistence. After any restart, redeploy or upgrade, every observation fails closed until credentials are re-injected.

That interacts badly with the version counter, which also resets. An attacker who captured an old envelope could replay it into a freshly restarted machine and install a superseded credential — which, if that credential has been revoked at Hex, is a denial of service. Two defences:

  • issuedAt freshness window (§4 step 5) — bounds the replay window across restarts, where the version counter cannot help. This is the load-bearing one.
  • Version monotonicity — covers reordering within a machine's lifetime.

Automated recovery

Because envelopes are ciphertext, the keeper can hold a current set and re-submit them when it observes not_configured, without ever being able to read them. It is submitting to an endpoint the spec says anyone may submit to, with signatures it cannot forge — so this grants the keeper no authority it did not already have. This resolves the open question from the previous design, where holding plaintext envelopes would have made the keeper a credential store.

The tension to settle: a short freshness window is safer but forces fresh admin signatures at every restart; a long one enables automation but widens replay. Suggest ~24h with prompt revocation at Hex on rotation, and re-signing as part of planned maintenance. Note replaying a current envelope is harmless — it installs what is already installed. Only superseded ones matter, so the window only needs to be shorter than the gap between rotation and revocation.

Readiness

  • Track presence per keyId; start unconfigured.
  • Fail price actions with a distinct not_configured class — never a generic source error, or the runbook sends someone to debug the wrong thing.
  • Expose booleans in /state ("hex key: present"), never values. /state is public.
  • Alert on it — the feed stales out shortly after.

Related to finding 12: the same readiness signal must distinguish stub mode. A hard-coded par price and a correctly-configured par price look identical from outside; the banner and StubMode() exist for exactly that reason, and not_configured must be equally loud.

9. What a third party can verify

  • Which token contracts, on which chains, and the price rule and quorum policy — from the image.
  • Which RPC providers are in use — from the instruction history. There is no allowlist to check them against: trusting the providers means trusting the owner key (Findings §15).
  • Who is permitted to set credentials — from the image, since the admin set is baked.
  • That the operator never saw the credentials — from attestation plus ECIES, provided §6's recommendation stands.

What they still cannot verify is whether Hex's API told the truth. No configuration design fixes that — see Findings §1.

Tests worth naming

  • SET_SECRET arriving as an on-chain instruction is rejected.
  • A Coston2-bound envelope is rejected on mainnet config.
  • An envelope for another teeId is rejected.
  • Threshold minus one signature is rejected; the same signature repeated to reach the threshold is rejected.
  • An expired issuedAt is rejected even at version 1 on a fresh process (the restart-replay case).
  • A failed SET_SECRET emits no value, length, or hostname in Log — same assertion style as finding 1's.
  • Any https host is accepted — TestAnyHostIsAccepted pins the no-allowlist decision, so reintroducing a constraint means changing a named test.

11. Open questions

  1. Admin set membership and M-of-N. Suggest 2-of-3.
  2. Freshness window length — trades restart automation against replay exposure (§7).
  3. Timelock on setEndpoints? How long is useful without being obstructive?
  4. Diversity rule k. Songbird has one working public endpoint, so any k > 1 needs paid coverage there.
  5. Does the proxy apply its own signature rules to unknown custom op types, or queue them unchecked? Our design does not depend on the answer — the extension verifies regardless — but it is worth knowing whether an unauthorised SET_SECRET is dropped at the proxy or reaches us and is rejected there.
