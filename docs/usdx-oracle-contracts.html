1. UsdxInstructionSender

Start from the scaffold's InstructionSender.sol. The constructor, setExtensionId() and _getExtensionId() are marked do not modify — leave them. Replace the two greeting functions with one:

bytes32 public constant OP_TYPE_USDX_ORACLE = bytes32("USDX_ORACLE");
bytes32 public constant OP_COMMAND_GET_PRICE = bytes32("GET_PRICE");

function requestPriceUpdate() external payable {
    address[] memory teeIds = TEE_MACHINE_REGISTRY.getRandomTeeIds(_getExtensionId(), 1);
    address[] memory cosigners = new address[](0);

    ITeeExtensionRegistry.TeeInstructionParams memory params =
        ITeeExtensionRegistry.TeeInstructionParams({
            opType:             OP_TYPE_USDX_ORACLE,
            opCommand:          OP_COMMAND_GET_PRICE,
            message:            "",            // no caller input; see below
            cosigners:          cosigners,
            cosignersThreshold: 0,
            claimBackAddress:   msg.sender
        });

    TEE_EXTENSION_REGISTRY.sendInstructions{value: msg.value}(teeIds, params);
}

The instruction carries no payload. Everything the extension needs — which chains, which tokens, which endpoints — is fixed in the image. Accepting caller-supplied parameters would let whoever triggers an update influence what gets measured, which defeats the point. The scaffold's docs note that message is "typically non-empty"; empty is fine and is the right choice here.

Endpoint configuration

Only endpoints go through this contract. Credentials are delivered off-chain by direct instruction and never touch the sender — see Configuration & Secrets. That keeps the whole secret-handling path out of Solidity.

function setEndpoints(address teeId, bytes calldata config) external payable onlyOwner;
Explicit teeIdNot getRandomTeeIds. Configuration must land on a named machine, not a random one, or machines silently drift apart. Provisioning N machines is N calls.
onlyOwnerAn open setter is a denial-of-service hole — and worse here, endpoint selection is data-source selection. The extension-apikey reference leaves its equivalent unrestricted: correct for a demo, not for us.
Plaintext is intendedPublishing which providers we read is the point. The credential portion is substituted inside the enclave from a placeholder, so nothing secret appears in calldata.
Consider a timelockThe change is public, so a delay gives observers a chance to notice a wrong-looking endpoint set before it takes effect — which is most of the reason to put it on-chain at all.

Who may call requestPriceUpdate()

OptionTrade-off
Open to anyoneBest liveness — anyone can refresh a stale feed. Each call costs the registry fee, so spam is self-limiting, but a determined griefer could still burn our TEE capacity.
Keeper allowlistPredictable load, but the feed's freshness now depends on our keepers being alive.
Open + minimum interval (proposed)Permissionless, with a per-caller or global cooldown matching the 10-minute source refresh. Rejects the pathological case without centralising liveness.

2. UsdxStateVerifier

TeeExtensionRegistry.register(teeExtensionStateVerifier, teeExtensionInstructionsSender) requires a state-verifier address, and the scaffold does not ship one — this is a gap that will bite at registration time if nobody notices it first.

Our extension's state is operational telemetry, not consensus-critical, so a permissive verifier is correct for v1. Write it deliberately rather than by accident, and document that it is intentionally permissive so a future reviewer does not mistake it for an oversight.

3. UsdxPriceStore — the security boundary

Everything else can be sloppy and the system still works. If this contract accepts something it shouldn't, the feed is wrong and every downstream protocol is wrong with it.

Acceptance rules

The message layout is defined normatively in Extension §6. This must decode exactly that.

function submitPrice(bytes calldata body, bytes calldata signature) external {
    // 1. authenticity — note the EIP-191 prefix: tee-node signs accounts.TextHash(keccak256(body)),
    //    so recovering against the bare keccak256 silently yields the wrong address.
    bytes32 digest = MessageHashUtils.toEthSignedMessageHash(keccak256(body));
    address signer = ECDSA.recover(digest, signature);
    require(machineRegistry.isActiveFor(EXTENSION_ID, signer), "not a registered TEE");

    PriceReport memory r = abi.decode(body, (PriceReport));

    // 2. schema — a signature for another layout or output scale is not valid here.
    //    There is deliberately no chainId/store/feedId binding: where a report lands
    //    is settled by the registry check above, not by the payload.
    require(r.domain   == DOMAIN,            "wrong domain");
    require(r.decimals == EXPECTED_DECIMALS, "unexpected decimals");

    // 3. configuration binding — the report commits to the config it was computed
    //    under, and that must match what setEndpoints published for THIS machine.
    //    Without it the on-chain config records only what was SENT: a rejected
    //    payload or an undelivered instruction leaves a machine publishing valid
    //    prices from stale configuration, and with several machines one that never
    //    received its call does so indefinitely.
    bytes32 expected = configSource.expectedConfigHash(signer);
    require(expected != bytes32(0),          "no config published");
    require(r.endpointsHash == expected,     "stale config");

    // 4. ordering + replay, in one rule
    require(r.observedAt > lastObservedAt, "stale or replayed");

    // 5. clock sanity
    require(r.observedAt <= block.timestamp + MAX_SKEW, "from the future");
    require(r.observedAt >= block.timestamp - MAX_AGE,  "too old to matter");

    // 6. plausibility — reject, never clamp
    require(r.price >= minPrice && r.price <= maxPrice, "out of bounds");

    // 7. optional deviation guard — see below
    ...
    lastObservedAt = r.observedAt;
    lastPrice      = r.price;
    emit PriceUpdated(r.price, r.observedAt, signer, r.instructionId);
}
Hash the bytes you were given, don't re-encode. Taking keccak256(body) on the exact calldata — rather than decoding to a struct and re-encoding it — removes any chance of an encoding round-trip mismatch between the Go producer and the Solidity verifier. Decode the same bytes separately to read the fields.
RuleWhy it is there
Signer is a registered, active machineChecking "is a TEE" is not enough — it must be a TEE for our extension, and still active. A decommissioned machine's key must stop working.
Domain, chain, store, feed all bound in the signatureThe chainId check is the one that matters most in practice: we will run this on Coston2 first, plausibly with the same machine and therefore the same key. Without it, every testnet price is a valid mainnet submission.
Strictly increasing observedAtFCC is explicitly fire-and-forget with no ordering guarantee. This single rule covers replays and out-of-order delivery together. Do not reach for a nonce; the timestamp is already the right key.
Reject out-of-bounds, don't clampClamping publishes a number nobody computed and hides the fault. Rejecting keeps the last honest value and raises an alert.
Permissionless submissionThe signature is the authority. Restricting submission would add a liveness dependency for no security gain.
Governance pause()Freezes the value. Must not make reads revert — see §4.

The deviation guard — unresolved

This needs a named risk owner and is blocking. A guard that rejects large jumps protects the feed from one bad data point, but delays detection of a genuine depeg — the exact scenario the feed exists for. These pull in opposite directions and it is not an engineering call.

Straw man to react to: upward moves toward 1.0 publish freely; a downward move beyond maxDeviationBps requires K≈3 consecutive confirmations (~15 min at a 5-minute cadence) but pages on the first observation. Someone must consciously accept that a real depeg reaches consumers ~15 minutes late.

4. UsdxCustomFeed

Interface verified against flare-smart-contracts-v2:

interface IICustomFeed {
    function getCurrentFeed() external payable returns (uint256 _value, int8 _decimals, uint64 _timestamp);
    function feedId()        external view    returns (bytes21 _feedId);
    function calculateFee()  external view    returns (uint256 _fee);
}
MutabilitygetCurrentFeed() is payable and not view. Our implementation must match even though it only reads storage.
FeecalculateFee() returns 0. The shipped sFLR/stXRP feeds charge because their consumer is really paying for an underlying FastUpdater read; we have none.
We are a primary feedBoth shipped examples are derivative — they read an underlying FTSO feed and rescale it by an exchange rate. We serve a value our own TEE produced. Allowed (the registry checks only category and interface), but their logic is not a template. Only their structure is.
Never revert. FtsoV2.getFeedById forwards the call, so a revert inside getCurrentFeed() propagates to every consumer at once — converting our stale-data problem into their liveness outage, simultaneously, across every protocol reading the feed. Return the last stored price with its true ageing timestamp and let consumers apply their own freshness policy. The same applies to pause: freeze the value, do not throw.

Feed ID

bytes21 = 1 category byte + 20 bytes ASCII name, right-padded with zeros by the bytes21 cast. Custom feeds must use a category in 32–63 — _isCustomFeedId checks 32 <= category < 64. It is a range, not one specific byte.

category 0x20 + "USDX/USD"
0x20  555344582f555344  000000000000000000000000
feedId = 0x20555344582f555344000000000000000000000000

Agree the name with Flare before registering. Integrators hard-code the feed ID, so renaming later means either a migration or leaning on feedIdChanges. Decimals (proposed 8) are unconstrained by the interface — entirely our call.

Design consequence: keep UsdxCustomFeed as thin as possible. Every line of logic in it is a line that can only be fixed through governance. Put the rules in the store, and the judgement in the enclave.

7. Testing

  • Fuzz the store's guards. Random observedAt orderings must never leave lastObservedAt going backwards; random prices outside bounds must always revert.
  • Signature negative cases: unregistered signer, deactivated machine, signature over a different observedAt than the body carries, replayed body.
  • Domain separation, with a real fixture: take a body signed for Coston2 and assert mainnet rejects it. Also wrong domain, wrong store, wrong feedId. These are the checks most likely to be quietly dropped as "obviously fine".
  • Cross-language signature fixture: a body produced and signed by the Go extension, committed as a fixture, verified by the Solidity test. This is what catches the EIP-191 prefix and the v = 0/1 vs 27/28 mismatch — neither shows up when both sides are written by the same person assuming the same thing.
  • Staleness path: assert getCurrentFeed() returns rather than reverts when the stored price is arbitrarily old, and when paused. This is the test most likely to be forgotten and the most damaging to miss.
  • Feed ID: assert the category byte lands in 32–63 and that addCustomFeeds would accept it.
