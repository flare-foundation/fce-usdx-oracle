1. The container contract we must satisfy

Normative source: docs/extension-contract.md. It is not ours to change — any conforming container is a valid extension, and ./scripts/test-conformance.sh enforces it mechanically.

SurfaceRequirement
POST /actionReturns ActionResult JSON with HTTP 200 whenever a handler ran — including when it failed. Handler failure is signalled by ActionResult.status, never by HTTP status. 400 for unparseable input, 501 for an unrouted (opType, opCommand).
GET /stateReturns StateResponse (200). Serialised against handlers, so a state read never sees a half-applied mutation.
RoutingGET /action → 405 · POST /state → 405 · anything else → 404
ConcurrencyHandler invocations are serialised; at most one runs at a time.
Calls outPOST /sign and POST /decrypt on $SIGN_PORT. Wire encoding there is base64, not hex — the single most common porting mistake.
Two encoding traps from the contract doc. ActionResult.version is a plain string ("0.1.0") while StateResponse.stateVersion is bytes32 — genuinely asymmetric, and other repos have got it wrong. And ActionResult.data must be byte-exact: Hash() computes keccak256(data) and that hash is signed, so emit compact JSON with no whitespace in declaration order.

3. Acquiring the sources

Five reads per update: three chains and two API endpoints. Fetch them concurrently under one global deadline — total time matters because it bounds the inconsistency window (§5).

3a. Supply, per chain

The block-selection rule is the subtle part. Providers disagree on latest, and — measured — also on finalized, so never send a tag in the query.

for each chain:
    # 1. resolve every provider's view of the finality reference to a NUMBER
    for p in providers:
        h[p] = (chain == ethereum)
                 ? eth_getBlockByNumber("finalized").number
                 : eth_blockNumber()

    # 2. the lowest common view — everyone can serve at or below this
    H = min(h)

    # 3. back off by the per-chain margin
    B = H - margin[chain]

    # 4. refuse if B is outside the shallowest provider's state window
    if (H - B) > min_state_window[chain]:
        fail("margin exceeds provider state retention")

    # 5. every provider answers the SAME explicit block
    for p in providers:
        s[p] = eth_call(token[chain], totalSupply(), at=B)

    # 6. quorum on identical values — not a median
    require count(most_common(s)) >= quorum[chain]
    raw = most_common(s)

    # 7. normalise with per-chain decimals
    supply[chain] = raw / 10 ** decimals[chain]
Identical, not medianAt a fixed block these reads are deterministic. Disagreement means something is wrong — a median would paper over it.
Per-chain marginsMeasured block times: Flare 1.11 s, Songbird 1.07 s, Ethereum 12.01 s. 60 s of margin is ~54 blocks on Flare but ~5 on Ethereum.
State windowsProvider retention ranges from latest only to full archive. Two Ethereum endpoints keep 64 blocks; Ethereum finalized already sits ~83 behind head, so a naive margin on top of that will fall outside their window.
DecimalsRead them; never hard-code. Ethereum is 18, Flare and Songbird are 6. Caching per deploy is fine — but read at least once and assert.
SongbirdOnly one public RPC exists. Quorum there is currently 1-of-1 unless we buy coverage or self-host — a decision, not a default.

3b. Reserves, from Hex

The two endpoints do not return the same shape. Give them separate types and separate validation; a shared struct with a uniform currency == "USD" assertion fails closed on the public endpoint forever, because that endpoint has no currency field.

CheckPublic (bonds)Private (cash)
Thousand separators in valuepresent — must stripabsent in the sample
currencyabsent — do not requirerequire "USD"
last_update freshnessreject if older than maxReserveAgesame
Parsearbitrary-precision decimal, never float64
Boundsnon-negative, finite, within a plausible order of magnitude
Strip separators carefully. Blindly deleting commas is how you mis-parse a comma-as-decimal-point locale: "1,50" silently becomes 150. Validate the shape — digits, grouped in threes, one dot, two decimal places — and reject anything else rather than "cleaning" it.

4. Computing the price

S = Σ supply[chain] − exclusions          # decimal, not float
B = R_cash + (1 − haircut) · R_bonds      # haircut defaults to 0

guard S > 0                               # else fail closed
guard B ≥ 0

ratio = B / S
price = min(1, ratio)

value = truncate(price · 10^decimals)     # round DOWN, never up
  • Decimal arithmetic throughout. big.Rat or shopspring/decimal. A float64 cannot represent these magnitudes exactly and the whole point is cent-level fidelity.
  • Truncate rather than round so we never over-report backing.
  • Cap at 1. USDX redeems at par; over-collateralisation does not make it worth more.
  • The haircut parameter exists but defaults to 0. Wire it now so applying one later is a config change, not a code-hash change — but do not apply one until Hex tells us how bonds are valued.
Reality check. With today's inputs this computes exactly 1.000000, and — per Findings §1 — it may be structurally incapable of computing anything else. Build the arithmetic correctly regardless, but do not mistake a passing test suite for a working oracle.

5. The timing problem

Supply reads and reserve reads are not atomic. A redemption landing between them changes both sides:

  • Reserves read before the redeem (high) + supply read after the burn (low) → price over-stated.
  • Supply read before the burn (high) + reserves after (low) → price under-stated.

This is not hypothetical. A single burn of 1,000,000 USDX — 4.8% of supply — landed at 07:10:58Z on 31 Jul 2026, and supply has fallen 54% in six months. A redemption that size landing mid-update moves the naive ratio far more than any sane deviation threshold.

Mitigation: conservative double-read

S₁ = read_all_supplies()
R  = read_reserves()
S₂ = read_all_supplies()

if elapsed(S₁ … S₂) > consistency_window:  fail closed
S = max(S₁, S₂)        # bias every skew downward, never upward

Taking the larger supply against the observed reserves means any timing skew can only understate the price. Combined with the cap at 1, the error is one-directional and safe: we may briefly under-report backing, never over-report it. Cost is one extra round of RPC reads.

But note the source cadence. The public endpoint refreshes on a ~10-minute tick, so a consistency window measured in seconds is theatre against that input — it only constrains our own read spread. The real fix is a reserve figure with an as_of we can align to a block. Worth asking Hex for.

6. The on-chain message — canonical definition

This section is normative. The Contracts doc consumes exactly this; if the two ever disagree, this one wins. Any change here is a wire-format break requiring a new domain tag.

6a. Two different signatures — don't confuse them

SignatureOverFor
Result signaturehash(hash(data), id, hash(submissionTag), status)The proxy, to confirm the result came from the right machine. Per the FCC spec it is "not intended to be shared externally". Not what the store verifies.
Our embedded signaturethe price report body, belowThe store. The FCC spec expects data to be "self-contained in terms of actual result and proofs by provided signatures" — this is that proof.

6b. The signed body

Price only — no supply or reserve components (Findings §1; /state is public too, so they have nowhere to go).

struct PriceReport {
    bytes32 domain;         // keccak256("USDX_ORACLE_PRICE_V1")  — purpose + format version
    uint256 price;          // truncate(price · 10^decimals)
    int8    decimals;       // 8
    uint64  observedAt;     // measurement time — the store's monotonicity key
    bytes32 instructionId;  // the instruction that triggered this update
    bytes32 endpointsHash;  // keccak256 of the SET_ENDPOINTS payload in force
}

body      = abi.encode(report)          // NOT encodePacked
data      = abi.encode(body, signature) // ActionResult.data — bytes, bytes

Carry body as raw bytes, not as a re-encodable struct. The store then hashes the exact bytes that were signed instead of re-encoding a decoded struct and hoping the encoding round-trips identically. It also decodes those same bytes to read the fields — one source, no ambiguity.

6c. Why each field is in the signature

No target binding, by decision. The payload carries no chainId, store or feedId. Where a report is accepted is settled by the store's trust anchor instead — a signature is only accepted from a TEE machine currently registered to that store's extension. The payload binds what was observed and under what configuration; the registry check binds where it lands. The trade is that a genuinely-signed report can be replayed into another deployment registered under the same extension, though nobody can forge a price.

FieldAttack it prevents
domainA signature produced for some other USDX_ORACLE message being reinterpreted as a price. Also versions the format — changing the layout means changing this tag.
price, decimalsReinterpreting a value at the wrong scale — 1.0 at 8 decimals is 0.00000001 at 18.
observedAtRe-timing an old price under a fresh timestamp. It is the store's ordering key, so it must be signed.
endpointsHashA machine running configuration other than what was published. The store compares this against expectedConfigHash[teeId] from setEndpoints. Without it the on-chain configuration is advisory — it records what was sent, never what a machine is running. A rejected payload, an undelivered instruction, or (with several machines) one that never received its call, all leave a machine publishing perfectly valid prices from stale configuration.
instructionIdNot security-critical — an audit trail linking the price to its triggering event.

6d. How POST /sign actually signs — read this before writing the verifier

Traced through tee-node (internal/extension/server/server.go → internal/node/node.go → pkg/utils/crypto.go):

// we send:      { "message": base64(body) }
msgHash  := crypto.Keccak256(request.Message)                    // 1. hash our bytes
sig, _   := crypto.Sign(accounts.TextHash(msgHash), privateKey)  // 2. EIP-191 prefix, then sign
// we receive:  { "message": base64(...), "signature": base64(65 bytes) }
Two traps, both silent.
  1. tee-node applies EIP-191 prefixing. accounts.TextHash prepends "\x19Ethereum Signed Message:\n32" to the hash and re-hashes. So the store must recover against toEthSignedMessageHash(keccak256(body)), not against keccak256(body). Verifying the unprefixed hash simply recovers a different address, and it will look like a registry problem rather than a hashing one.
  2. v comes back as 0 or 1, because go-ethereum's crypto.Sign returns it that way. Solidity's ecrecover and OpenZeppelin's ECDSA.recover expect 27 or 28. Somebody must add 27 — decide whether it is the extension or the contract, and write a test that would fail if both or neither did it.

Also note the request/response encoding is base64, not hex — SignRequest.Message is a Go []byte and Go marshals those as base64 in JSON. Same trap as /decrypt.

7. GET /state — public, so keep it operational

/state is folded into the attested TEEState and republished by the proxy. It is a monitoring surface, not a private log.

Open question in the plan: whether to expose a short price history. It is useful for monitoring and harmless on its own — a series of published prices reveals nothing the feed doesn't already — so probably yes, bounded to a fixed ring.

8. Error taxonomy

The contract gives us status and log. Status 1 is success, 0 is failure, anything else is "in progress" — we have no in-progress state, so we only use 0 and 1.

ClassCauseMonitoring should
source_unavailableHex API or RPC timeout / 5xxwarn; page if sustained past 2 cycles
source_malformedunparseable value, missing field, bad shapepage — this means the contract changed
source_stalelast_update older than the boundwarn, page if sustained
quorum_failedproviders disagreed at a fixed blockpage — should be near-impossible
block_unavailablechosen block outside provider state windowpage — margin is misconfigured
consistency_windowread spread exceeded the boundwarn; frequent means the deadline is too tight
implausiblesupply = 0, ratio outside sane boundspage

Emit log = "error: <class>: <detail>" and keep only the class in /state. The detail may contain values we have agreed not to publish, and log travels with the result.

9. Configuration

Full treatment in Configuration & Secrets — inventory, delivery mechanism, ordering hazards and access control. Summary:

TierWhatDelivery
Bakedtoken addresses, chain IDs, price rule, quorum, exclusions, Hex URLs, permitted RPC hostscompiled in — covered by the code hash
EndpointsRPC endpoint descriptors, timeoutson-chain instruction, plaintext — publicly verifiable
CredentialsHex API key, RPC credentialsdirect instruction — off-chain, admin-signed, ECIES to that machine's key
Operator envports, log level, proxy URL, modemust appear in the allow_env_override label or attestation rejects it

Three implications the handler code has to carry:

  • A USDX_CONFIG op type with SET_ENDPOINTS (arrives as an instruction) and SET_SECRET (arrives as a direct action). SET_SECRET must reject anything not of type "direct", verify an M-of-N admin signature threshold itself — FCC gives no signer guarantee for direct actions — and return nil data with a fixed log string.
  • A readiness state. Secrets are memory-only and do not survive a restart, so the extension starts unconfigured and must fail price actions with a distinct not_configured class until provisioned.
  • A version check on config payloads. FCC has no ordering guarantee, so two rotations can land out of order and reinstate an old key. Same monotonicity rule as the store's observedAt.
