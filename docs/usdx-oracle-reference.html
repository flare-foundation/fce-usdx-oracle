1. Does Hex's reserves figure actually measure reserves?

Probably not — and this blocks the design. current_reserves_amount equals total on-chain supply to the cent and tracks it through changes. Under every explanation we can construct, backing / supply is pinned at 1.000000 and the feed can never report a depeg.

The observation

Supply, 3 live contracts25,452,544.524018
API current_reserves_amount25,452,544.52

Ruling out coincidence

A single match could be luck, so we looked for a supply change. Flare's RPC serves archive state, and bisecting found one 5.6 hours before the measurement:

block 66310829 @ 2026-07-31T07:10:58Z
  21,620,459.685024  ->  20,620,459.685024      delta -1,000,000.000000 exactly

The API's current value equals the post-burn sum — so it moved down by 1M within hours of the burn. It is not a frozen coincidence; it tracks.

Two readings, both fatal

  1. Derived from chain supply. The metric is computed from token supply, not from custody balances — in which case it is not a measurement of assets at all.
  2. Genuinely 1:1 par-backed. Every mint adds and every redemption removes the same amount from both sides, with yield swept out. A real number, but structurally incapable of falling below supply.

We initially assumed only (1) and had to correct: a 1M redemption should reduce both token supply and reserves by exactly 1M under perfectly ordinary accounting. The tracking behaviour does not distinguish the two. But it does not need to — under either reading backing/supply = 1.000000 by construction, cash is added on top, and the feed prints $1.00 forever.

The question that settles it

"Under what circumstances would current_reserves_amount ever be less than total on-chain supply?"

If the answer is never, or only if we manually write down a loss, then this oracle measures nothing and we need a different source — mark-to-market bond valuations, or an independent custody attestation.

Limitation of our evidence: the API exposes no history (we probed for it — unknown metric names return 500, there is no docs or OpenAPI endpoint), so "it tracks" is inferred from one observed supply change, not a time series.

Decimals differ across chains

Ethereum is 18, Flare and Songbird are 6. Normal for a LayerZero OFT (local decimals differ, shared decimals are 6), but hard-coding 6 would overstate the Ethereum leg by 10¹². Read decimals() per chain.

There is a second, older Ethereum contract

0x7A48…D56c still holds 150,000 USDX and is excluded from Hex's reserves figure — that is exactly the gap between the three-contract sum and the four-contract total. If we count it and Hex doesn't, we publish a spurious 0.6% depeg. Today the cash buffer masks the difference; that is luck, not design.

Songbird counts as real backed issuance

Counter-intuitive for a canary network — we expected a test deployment. But the arithmetic in §1 only closes if Hex treats those 1.16M as real, backed issuance.

Bridging is burn-and-mint, so summing is safe

USDX is a LayerZero OFT. On both Flare and the current Ethereum contract, token() returns the contract's own address — the native burn-and-mint pattern. A lock-and-mint adapter would return a different underlying ERC-20. So bridging burns on the source and mints on the destination, and summing totalSupply() does not double-count. This was the plan's biggest open risk; it looks resolved, but it is worth one line of confirmation from Hex.

Parsing gotchas

  • Comma separators break decimal parsing. "25,452,544.52" is not a valid decimal literal. Strip separators — but validate the shape rather than blindly deleting commas, since comma-as-decimal-point is a real locale convention and blind stripping turns "1,50" into 150.
  • The public endpoint has no currency field. The planned "reject if currency != USD" rule, applied uniformly, would fail closed on it forever. Validate per endpoint — do not share one response struct.
  • The private sample has no separators while the public has them. Do not assume the two formatters match; handle both formats on both endpoints.
  • Parse as arbitrary-precision decimal, never float64.
  • The private URL returns 404 without credentials, not 401/403 — so we cannot distinguish "no access" from "wrong path" until the key arrives. Ask Hex to confirm the path.
  • last_update ticked 12:17:21 → 12:27:21 → 12:37:21 with an unchanged value: a 10-minute refresh. Polling faster than that buys nothing.

Three findings that changed the design

  • finalized is not a shared truth. All live Ethereum endpoints support the tag and sit ~83 blocks (~17 min) behind head — but 1rpc.io resolved it to a block 32 earlier than the others. The tag has the same disagreement problem as latest, just smaller. Resolve it to a block number per provider, take the minimum, then query everyone at that explicit number — the same rule we already chose for latest.
  • State-retention varies from "latest only" to full archive. latest − N must stay inside the shallowest configured provider's window (64 blocks on two Ethereum endpoints), or those providers drop out of quorum every round.
  • Measured block times: Flare 1.11 s, Songbird 1.07 s, Ethereum 12.01 s. N is per-chain, not global — 60 s of margin is ~54 blocks on Flare but ~5 on Ethereum.

We never need eth_getLogs — only eth_call, eth_blockNumber and eth_getBlockByNumber. Worth recording because Flare's public RPC caps log ranges at 30 blocks, which looks like a blocker until you notice we don't use it.

For production, assume keyed endpoints. Public RPCs rate-limit and vanish — three endpoints named in the original plan had already died by the time of this survey. Primary should be paid (QuickNode, dRPC, Ankr premium), with public endpoints as the third leg. The keys live inside the TEE.

5. What does the FTSO custom feed interface require?

Verified against flare-smart-contracts-v2 source, not the public docs:

interface IICustomFeed {
    function getCurrentFeed() external payable returns (uint256 _value, int8 _decimals, uint64 _timestamp);
    function feedId()        external view    returns (bytes21 _feedId);
    function calculateFee()  external view    returns (uint256 _fee);
}
  • getCurrentFeed() is payable and not view — our implementation must match the mutability even though we only read storage.
  • We are a primary feed; both shipped examples are derivative. SFlrCustomFeed and StXrpCustomFeed read an underlying FTSO feed from FastUpdater and rescale it by an exchange rate. We serve a value our own TEE produced, with nothing upstream. Allowed — the registry only checks category and interface — but it means we can borrow their structure and none of their logic.
  • calculateFee() returns 0. The shipped feeds charge because their consumer is really paying for the underlying read; we have no underlying read.
  • Reverting is a consumer-facing outage. FtsoV2.getFeedById forwards the call, so a revert propagates to every caller. Hence the decision that getCurrentFeed() never reverts on staleness — it returns the last price with its true, ageing timestamp, and pause freezes the value rather than throwing.

Feed ID encoding

bytes21 = 1 category byte + 20 bytes ASCII name, right-padded with zeros by the bytes21 cast. Custom feeds must use a category in 32–63 (0x20–0x3F) — FtsoV2._isCustomFeedId checks 32 <= category < 64. It is a range, not one specific byte; the value inside it is our choice.

category 0x20 + "USDX/USD"

0x20  555344582f555344  000000000000000000000000
 cat   "USDX/USD"        12 bytes of padding

feedId = 0x20555344582f555344000000000000000000000000

Registration and upgrades

  • FtsoV2.addCustomFeeds(IICustomFeed[]) is onlyGovernance — a Flare governance proposal with whatever timelock that carries. Treat it as a scheduling dependency, not a deploy step. Reverts with "invalid feed category" outside 32–63, "feed already exists" on a duplicate.
  • replaceCustomFeeds(IICustomFeed[]) repoints an existing feed ID at a new contract, so we can fix bugs without integrators re-integrating. Keep the feed contract thin — a read adapter over UsdxPriceStore — so most changes never need a governance action.
