Why this shape

ChoiceReasoning
Steps (4) and (5) are separate, and (4) runs on a timer Forced, not chosen. tee-node allows an extension 2 seconds to answer an action — a const in its internal package, not configurable — and a complete observation measured 2.0–2.9 s, so every request timed out with status 3 and no price ever reached the chain. Observing cannot happen on demand; signing cannot happen in advance, because the body binds instructionId. So the slow half runs every 2 minutes and the request costs one signature. Staleness is bounded at 10 minutes, past which the extension publishes nothing. Findings §23.
Keeper relays the result; the TEE broadcasts nothing Signing a transaction inside the enclave would mean managing gas price, nonces, stuck-transaction replacement and a funded wallet there. The store verifies the TEE signature, so a keeper cannot forge or alter a price — it can only fail to deliver one, which is a liveness problem we solve by running more than one. Submission is permissionless.
Direct RPC rather than FDC attestation FDC would add a round trip and considerable complexity to obtain data we can read directly, and the TEE is already the trust anchor for everything else in the pipeline. We buy robustness with provider redundancy instead.
Price computed inside the enclave, not by the keeper The whole value proposition is that the computation is pinned by a registered code hash. A keeper computing the price would make the TEE decorative.
A store contract separate from the feed contract replaceCustomFeeds lets governance repoint a feed ID at a new contract. Keeping the feed a thin read adapter means most fixes land in the store or the extension and never need a governance action.

2. Trust model

What the TEE actually gives us

  • Code integrity. The container's code hash is registered on-chain via addTeeVersion. Attestation proves the machine is running that image, so anyone can verify which program produced a price.
  • Secret confidentiality. The Hex API key and RPC credentials are injected encrypted to the TEE's public key and decrypted inside the enclave via POST /decrypt. The operator never sees them in plaintext.
  • Authenticity of the result. The result is signed with the TEE identity key; the store checks the recovered address is a registered, active machine for our extension.

What it does not give us

The TEE cannot make bad input good. If Hex's API reports a wrong reserve figure, the enclave will faithfully compute and sign a wrong price. Attestation proves provenance and integrity, never truthfulness of external data. This is why the §1 premise check in the Findings mattered — no amount of TEE engineering compensates for a source that cannot express the condition we are trying to detect. That check is resolved (the figure is a bank-reported balance), but the principle stands for any future source change.
  • No protection against source compromise. Mitigated only by bounds checks, alerting and a governance pause.
  • No ordering guarantee. FCC is explicitly "fire and forget". Two price updates can arrive out of order, which is why the store enforces strictly increasing observedAt rather than assuming sequence.
  • No availability guarantee. A machine can be down, an instruction can be lost. The design must degrade to "stale but honest", never to "fresh but wrong".

3. What is public

This caught us out once and is worth stating plainly. The extension's GET /state is not a private channel. tee-node polls it, folds the response into TEEState.state, and the TEE proxy publishes that — attested — at GET /info. Anything placed in /state is world-readable with a signature attached, arguably more exposed than the on-chain payload since it updates continuously rather than once per instruction.

Consequence: if Hex treats reserve figures as confidential, they can live in none of these. The practical cost is that consumers cannot independently recompute min(1, B/S) from public data — they can verify which code ran, but not what it saw. A lagged disclosure (say T+24h) would restore auditability without revealing live positions; worth proposing to Hex.

The one rule that ties these together: every failure degrades toward stale but honest. The feed's timestamp is the honest signal, and consumers must check it. A revert would convert our outage into theirs, simultaneously, across every protocol reading the feed.

5. Deployment topology

The extension runs as a single container on a GCP Confidential Space VM alongside tee-node. Go extensions can use the single-process shape — the scaffold's go/cmd/docker/main.go starts teeServer.StartServerExtension(configPort, signPort, extensionPort) in a goroutine next to the extension's own HTTP server, producing one static distroless binary. That is the most reproducible option and we should keep it.

Ports5501 config · 7701 sign (extension → tee-node) · 7702 extension (/action, /state)
EgressHex API + RPC providers, via Cloud NAT with a reserved static IP per machine — Hex allowlists by IP
IngressNone from the internet. The proxy polls; the machine sits behind the firewall.
ScalingEach additional machine is another IP for Hex to allowlist. Decide the count before asking them.

Machine count is a real trade-off. More machines mean better liveness and no single point of failure, but every one needs its own allowlist entry, and adding one later is a coordination step with Hex rather than something we can do ourselves. Since results are individually signed and the store accepts any valid one, machines do not need to agree with each other — they are redundant, not a quorum. Two is probably the right starting point; that should be a decision rather than a default.
