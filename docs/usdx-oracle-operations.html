1. Keeper

A small, boring, stateless loop. It holds no authority — the store verifies the TEE signature — so its only job is liveness.

📎 Full implementation spec — step semantics, deadline budget, crash behaviour and the monitoring hooks: Keeper Specification.
every T:                                                  # single-flight, never overlap
    fee = operationFees.getOperationFee(USDX_ORACLE,      #    never hard-code the fee
                                        GET_PRICE)
    tx  = sender.requestPriceUpdate{value: fee}()         # 1. trigger
    id  = receipt(tx).logs.first(PriceUpdateRequested)    #    a tx returns nothing off-chain
              .instructionId
    result = poll(proxy, "/action/result/" + id,          # 2. collect
                  timeout = T/2, backoff = exponential)
    if result.status != 1:  record + alert; continue      # fail closed, don't submit
    (body, sig) = abi.decode(result.data, (bytes, bytes)) # 3. relay — data wraps both
    store.submitPrice(body, sig)

Three earlier lines of this sketch were not implementable: requestPriceUpdate() did not expose the instruction id, ActionResult has no signature field (data is abi.encode(body, signature)), and the fee was a hard-coded constant. Contracts and tooling were fixed on 5 Aug 2026; see the keeper spec.

Run at least twoIndependently, ideally in different environments. Submissions are idempotent — the second one hits the observedAt monotonicity check and reverts harmlessly. Budget for that wasted gas rather than trying to coordinate them.
Cadence TMatch the ~10-minute source refresh. Polling faster buys nothing but costs a registry fee and gas per cycle.
Never computeThe keeper must not derive, adjust or sanity-"fix" a price. If the result says failure, it relays nothing.
Stuck transactionsStandard replace-by-fee with a bounded ceiling. A submission that misses its window is not worth chasing — the next cycle supersedes it.
WalletHot, low-value, monitored. Its compromise costs gas, not correctness.

2. Secrets and egress

RPC provider keyspaid Ethereum / Flare / Songbird endpointsSame

Secrets are encrypted to the TEE's public key and decrypted inside the enclave via POST /decrypt on $SIGN_PORT. Remember that API is base64, not hex. Design the injection path so rotation never requires a new code hash — otherwise every key rotation becomes a re-registration and a re-attestation.

Static egress IPs are on the critical path and easy to miss. Hex allowlists by IP, so every Confidential Space VM needs a reserved static IP via Cloud NAT — and every machine needs its own allowlist entry. Adding a machine later is a coordination step with Hex, not something we can self-serve. Decide the machine count before asking them, and treat "add a TEE machine" as a multi-day task forever after.

What we can prove to a third party

Worth writing down explicitly, because it is the project's actual selling point. Attestation lets an outsider verify the machine runs a specific registered image, and the image's source determines exactly what it does with the keys. So: this price was computed by this code, which reads these endpoints, and the operator could not have seen the API key or altered the arithmetic. What it does not prove is that the endpoints told the truth — see Architecture §2.

A price below $1.00 is a business event, not a metric. It should page a human and there should be an agreed comms path to Hex before it ever fires — deciding who to call while it is happening is the wrong time. Under normal 1:1 operations (§1, resolved: the reserves figure is a bank-reported balance) a sub-$1 price should never print, which makes this alert both the depeg signal and a canary for the oracle working at all.

Backup and restore — open

FCC supports Shamir-based key backup and restore across TEE machines. Do we need it here? Our extension holds no user funds and no long-lived derived keys — it signs with the TEE identity key, and the store accepts any registered active machine. So losing a machine should mean registering a replacement, not restoring one. If that reasoning holds, we can skip backup entirely and treat machines as cattle. Worth confirming before assuming it.

5. Deployment

Follow docs/deployment-steps.md for the mechanics. Ordering notes specific to us:

  1. Reproducible build first. The code hash is registered on-chain, so build determinism is a security property. Go on distroless is bit-for-bit reproducible; keep the single-process shape.
  2. Static IP allowlisted before the machine is useful — without it the private endpoint is unreachable and every update fails closed.
  3. Governance feed registration in parallel, not at the end. It has a timelock and is the item most likely to add a week.
  4. Coston2 fully green before mainnet, including the failure drills.
  5. Shadow run on mainnet sources before any consumer is pointed at the feed.

Upgrading without a feed gap

Because the store accepts results from any registered active machine, a rolling upgrade works: register the new code version, bring up a machine on it, confirm it produces results that agree with the old one, then retire the old machine. The feed never goes stale because both are submitting during the overlap. Verify the agreement rather than assuming it — a divergence during overlap is exactly the signal you want before retiring the old version.

7. Consumer documentation

Whatever we ship, consumers need four facts. Getting the last one wrong is how oracle integrations cause incidents:

  • The feed ID and its name.
  • The decimals (proposed 8).
  • What the price means — a backing ratio capped at 1, not a market price. It will not track a market dislocation, and it is not a liquidation-grade price for a thin market.
  • They must check the timestamp. The feed never reverts on stale data by design, so a consumer that ignores _timestamp will happily use an arbitrarily old price. Say this loudly, more than once.
